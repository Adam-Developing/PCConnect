## 1. Why the schema is being changed at all

The current schema is not merely untidy — three specific properties of it are *causing defects*:

1. **No timezone anywhere.** `reminders.Time TIME` + `Date DATE` with no offset. The
   `verifications` table proves users exist in `Asia/Calcutta`, `America/Lima`,
   `America/Sao_Paulo` and `America/Guayaquil`. Their reminders fire at UK time (S2-07).
2. **`utf8mb3`.** Reminder text cannot hold an emoji, or most of Devanagari beyond the BMP subset
   MySQL's `utf8mb3` covers (S2-08).
3. **A mutable row used as a command queue.** `pcnames.Request` + `pcnames.Value` cannot express
   "two commands pending", "this command has expired", or "who sent this shutdown" (S2-03/04/05).

Everything else — text columns as join keys, no foreign keys, dead tables — is cost of change
rather than active breakage, and is fixed in the same pass because the migration is already
happening.

## 2. Entity model

```
                            ┌─────────────┐
                            │    users    │
                            └──┬───┬───┬───┘
        ┌──────────────────────┘   │   └───────────────────────┐
        │ 1:1                      │ 1:N                       │ 1:N
┌───────▼───────────┐    ┌─────────▼─────────┐      ┌──────────▼─────────┐
│ user_credentials  │    │      devices      │      │     reminders      │
└───────────────────┘    └────┬─────────┬────┘      └──────────┬─────────┘
                              │ 1:1     │ 1:N                  │ 1:N
        ┌─────────────────────┘         │            ┌─────────▼──────────────┐
┌───────▼────────────┐        ┌─────────▼────────┐   │ reminder_occurrences   │
│ device_credentials │        │    commands      │   └────────────────────────┘
└────────────────────┘        └─────────┬────────┘
                                        │ 1:N
                              ┌─────────▼────────┐
                              │  command_events  │
                              └──────────────────┘

users 1:N refresh_tokens (0..1 device_id)   users 1:N auth_challenges
users 1:N security_events                   users 1:N idempotency_keys
```

### 2.1 Aggregate boundaries

Four aggregates. A transaction never spans two of them.

| Aggregate | Root | Members | Invariant it protects |
|---|---|---|---|
| **Account** | `users` | `user_credentials`, `refresh_tokens`, `auth_challenges` | A credential change revokes every token in one atomic step |
| **Device** | `devices` | `device_credentials` | A device always has exactly one live secret |
| **Command** | `commands` | `command_events` | A status transition and its audit row are written together, or not at all |
| **Reminder** | `reminders` | `reminder_occurrences` | Occurrences are consistent with the series' RRULE |

## 3. Key modelling decisions

### 3.1 Two identifiers per row

`id BIGINT UNSIGNED` internally (dense, 8-byte, cache-friendly clustered index — MySQL's InnoDB
clusters on the PK, so a random UUID PK causes page splits on every insert) and
`public_id BINARY(16)` holding a **UUIDv7** externally.

UUIDv7 is time-ordered, so the secondary unique index on `public_id` stays roughly append-only
instead of writing randomly across the B-tree the way UUIDv4 would.

Exposing `id` in the API would leak the user count and invite enumeration; the current API does
exactly that (`{"ID": 1, "Username": 1008, ...}` in the reminders response).

### 3.2 The command id is generated by the client

This is the design's load-bearing idempotency property. The mobile app generates a UUIDv7 *before*
sending. If the request times out and the user taps again, or the offline queue replays on
reconnect, the server sees a duplicate `public_id` and returns the existing command rather than
issuing a second shutdown. Without this, "retry" and "shut my PC down twice" are the same operation.

### 3.3 Commands carry structured params, never a shell string

`commands.command_type` is a `VARCHAR` with a `CHECK` constraint over six values;
`commands.params` is `JSON`. There is no path by which a string from an HTTP body reaches a shell.
The current design stores an arbitrary 500-character string and the client dispatches on it — safe
today only because `executor.go` happens to hold an allow-list. That allow-list becomes the
*second* of two enforcement points, not the only one.

### 3.4 Presence is in Valkey, durability in MySQL

`devices.last_seen_at` is written at most once per minute (heartbeat coalescing). Live presence —
"is this PC connected right now" — is a Valkey key with a TTL, updated by the Socket.IO connection
lifecycle. Writing a presence heartbeat to MySQL on every ping, as `pcnames.Time` does today, turns
a read-mostly table into a write-hot one for no benefit.

### 3.5 `CHECK` constraints rather than `ENUM`

Adding a value to a MySQL `ENUM` rebuilds the table. Adding one to a `CHECK` is a metadata-only
`ALTER`. With one maintainer and no online-schema-change tooling, that difference is the difference
between a five-second deploy and a locked table.

### 3.6 Soft delete only where it earns its place

`users` and `reminders` get `deleted_at` (accidental deletion is recoverable, and account deletion
needs a grace period). `commands`, `command_events` and `security_events` are append-only and
purged by retention. Everything else is hard-deleted by `ON DELETE CASCADE`.

## 4. Index strategy

Every index below exists to serve one named query. Indexes with no named query are not created.

| Index | Query it serves | Shape |
|---|---|---|
| `ix_commands_device_pending` | Agent reconnects: "my undelivered, unexpired commands" | `(device_id, status, expires_at)` — equality, equality, range |
| `ix_commands_expiry_sweep` | Expiry job: "everything past its TTL" | `(status, expires_at)` |
| `ix_reminders_user_due` | App home screen: "my upcoming reminders" | `(user_id, is_completed, due_at_utc)` |
| `ix_reminders_due_sweep` | Scheduler tick: "due in the next 60s" | `(due_at_utc, is_completed, deleted_at)` |
| `uq_refresh_tokens_hash` | Every token refresh | unique, single-column |
| `ix_refresh_tokens_family` | Reuse detection: revoke the family | `(family_id)` |
| `ix_devices_user_status` | Device list screen | `(user_id, status)` |

Composite column order follows equality-then-range. The two `_sweep` indexes exist because those
background jobs otherwise become full scans that grow with the table.

## 5. Migration strategy: expand / contract

> **Changed by [ADR-0009](adr/0009-implementation-platform.md).** The v2 store is
> PostgreSQL while v1 remains MySQL, so the two shapes are no longer in one database
> and one transaction cannot write both. The sequence becomes
> expand → **replicated import** → verify → cutover → contract, and the one-way door
> moves from contract to *cutover*. The stage gates below still apply; the dual-write
> stage is replaced by an idempotent, resumable import with the same verification
> queries run continuously. See [ADR-0009 §"The two-engine migration"](adr/0009-implementation-platform.md)
> and `src/PCConnect.LegacyMigrator`.

The database is live and both production clients read it. The migration therefore never has a
moment where old code cannot run. Five stages per changed table:

```
 ┌────────┐   ┌──────────┐   ┌───────────┐   ┌─────────┐   ┌──────────┐
 │ EXPAND │──▶│ DUAL     │──▶│ BACKFILL  │──▶│ CUTOVER │──▶│ CONTRACT │
 │        │   │ WRITE    │   │ + VERIFY  │   │         │   │          │
 └────────┘   └──────────┘   └───────────┘   └─────────┘   └──────────┘
  add new      write both     copy history    reads move    drop old
  nullable     old and new    then prove      to new        columns
  structures   shapes         they match      shape         and tables
```

**Stage gates.** Nothing advances without its gate:

| Stage | Gate to advance |
|---|---|
| Expand | New objects exist in staging and production; no application reads them yet |
| Dual write | 100% of writes land in both shapes for 48 h with zero divergence alerts |
| Backfill | The verification queries in §5.1 return **zero** rows for 24 consecutive hours |
| Cutover | Reads served from the new shape in staging for 72 h; canary in production for 24 h |
| Contract | Legacy clients below the sunset threshold are under 1% of traffic (see [ADR-0008](adr/0008-api-versioning-and-legacy-sunset.md)) |

**Rollback.** Every stage before Contract is reversible by reverting the application, because the
old columns still exist and are still being written. Contract is the only one-way door, which is
why it is last and gated on client telemetry rather than on a date.

### 5.1 Verification queries

These run continuously during Dual Write and Backfill. Any non-zero result blocks the next stage.

```sql
-- V1: every legacy PC has exactly one device
SELECT COUNT(*) AS orphaned_pcs
FROM pcnames p
LEFT JOIN devices d ON d.legacy_pcid = p.PCID
WHERE d.id IS NULL;

-- V2: no reminder lost its text in the re-encryption
SELECT COUNT(*) AS unmigrated_reminders
FROM reminders
WHERE body_ciphertext IS NULL OR OCTET_LENGTH(body_ciphertext) < 29;  -- 12B nonce + 16B tag + >=1B

-- V3: every user has exactly one credential row
SELECT COUNT(*) AS credential_mismatch
FROM users u
LEFT JOIN user_credentials c ON c.user_id = u.id
WHERE c.user_id IS NULL;

-- V4: no command outlives its TTL unresolved  (must be 0 forever, not just in migration)
SELECT COUNT(*) AS stale_pending
FROM commands
WHERE status IN ('issued','delivered') AND expires_at < UTC_TIMESTAMP(3);

-- V5: dual-write divergence — legacy mailbox vs command table
SELECT COUNT(*) AS divergent
FROM pcnames p
JOIN devices d ON d.legacy_pcid = p.PCID
WHERE p.Value = 1
  AND NOT EXISTS (
    SELECT 1 FROM commands c
    WHERE c.device_id = d.id
      AND c.status IN ('issued','delivered')
      AND c.expires_at > UTC_TIMESTAMP(3)
  );
```

### 5.2 Charset conversion

> **Not required as built.** PostgreSQL is UTF-8 throughout, so S2-08 is closed by the
> choice of engine and there is no conversion stage, no index-prefix hazard and no
> low-traffic window to find. This section is kept as the record of what the MySQL
> path would have cost ([09 §2.6](09-implementation-notes.md)).

`utf8mb3 → utf8mb4` changes the maximum bytes per character from 3 to 4, which can overflow an
index prefix. Ordering matters:

1. Convert **table by table**, smallest first, during a low-traffic window.
2. `ALTER TABLE … CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci, ALGORITHM=INPLACE`
   where MySQL permits it; `pt-online-schema-change` or a shadow-table copy where it does not.
3. Any `VARCHAR(255)` that is part of a unique index and might exceed the 3072-byte InnoDB limit is
   shortened *first* — in this schema, `users.email` at 320 chars is the one to watch; it is indexed
   via `email_normalised` which stays inside the limit at `utf8mb4` because the practical RFC limit
   is 254 characters.
4. Verify with `SELECT … WHERE col <> CONVERT(col USING utf8mb4)` returning zero rows.

## 6. Password migration — the one that touches every user

~1,000 accounts hold an **unsalted client-side SHA-256** (S1-03). There is no way to derive the
original password, so a silent server-side rehash is impossible. The upgrade happens on next login:

```
  login(username, password_plaintext)          ← client now sends the real password over TLS
        │
        ├─ credential.algo == 'argon2id'
        │     └─▶ argon2id.verify(hash, password) ──▶ done
        │
        └─ credential.algo == 'legacy_sha256_unsalted'
              ├─ sha256(password) == hash ?
              │     ├─ no  ──▶ reject (constant-time compare, generic error)
              │     └─ yes ──▶ in ONE transaction:
              │                  hash    = argon2id(password)
              │                  algo    = 'argon2id'
              │                  must_rehash = 0
              │                  password_changed_at = now
              │                revoke every refresh token for the user
              │                write security_events(password_upgraded)
              │                ──▶ done
              └─ (accounts never seen again keep the legacy row until the deadline below)
```

**The client change is mandatory and comes first.** Today both clients SHA-256 the password
*before* sending it. During the transition the server accepts both `password` (new clients) and
`legacyPasswordHash` (old clients) on the login route, and the legacy path is only able to reach the
legacy comparison — it can never trigger an Argon2id upgrade, because the server never sees the real
password. That means:

- Accounts whose users update their client get upgraded automatically at next login.
- Accounts that never update **stay on the legacy hash** until the legacy login field is removed.
- At the sunset date, remaining `legacy_sha256_unsalted` rows are set to `status='pending_verification'`
  and those users are sent a password-reset email. No account is silently locked out without a
  recovery path.

`user_credentials.must_rehash` and `security_events` make the progress of this measurable:
`SELECT algo, COUNT(*) FROM user_credentials GROUP BY algo` is the migration's burn-down chart.

## 7. Reminder re-encryption

Currently every reminder is `AES-256-CBC(users.api_key, …)` (S1-06). The API key must be destroyed,
so the data must be re-encrypted first, in this order:

1. **Expand** — add `body_ciphertext`, `body_dek_id`; generate and wrap a DEK for every user.
2. **Backfill job** — for each user: decrypt with the still-present `api_key`, re-encrypt with the
   DEK under AES-256-GCM, write the new columns. Idempotent and resumable by user id; runs in
   batches with a bounded transaction size.
3. **Verify** — V2 above, plus a sampled round-trip: decrypt `body_ciphertext` and compare against
   decrypting the legacy column, for a random 1% and for every row of the maintainer's own account.
4. **Cutover** — reads move to `body_ciphertext`.
5. **Contract** — drop the legacy `Reminder` column, *then* drop `users.api_key`.

Dropping `api_key` before step 5 completes destroys every reminder irrecoverably. This ordering
constraint is the single most dangerous dependency in the whole migration and is called out again
in [07 §4 Phase 4](07-migration-plan.md).

## 8. Legacy-to-v2 field mapping

| v1 | v2 | Transform |
|---|---|---|
| `users.id` | `users.id` | preserved (FK stability) |
| — | `users.public_id` | generated UUIDv7 |
| `users.Name` | `users.display_name` | trim |
| `users.Username` | `users.username` + `username_normalised` | `lower()` |
| `users.Email` | `users.email` + `email_normalised` | `lower(trim())`; **duplicates must be resolved before the unique index is added** |
| `users.Password` | `user_credentials.password_hash`, `algo='legacy_sha256_unsalted'` | moved, then upgraded per §6 |
| `users.Enabled` | `users.status` | `1 → 'active'`, `0 → 'suspended'` |
| `users.DateTimeOfSignup` | `users.created_at` | `STR_TO_DATE`, assume `Europe/London`, convert to UTC |
| `users.DateOfBirth` | *dropped* | never read by any client; removing it shrinks the PII surface |
| `users.MailingList` | `users.is_marketing_opt_in` | cast |
| `users.api_key` | *dropped* | after §7 completes |
| `pcnames.PCID` | `devices.legacy_pcid` (temporary) → `devices.id` | mapping column dropped at Contract |
| `pcnames.UserID` | `devices.user_id` | preserved |
| `pcnames.PCName` | `devices.display_name` | trim; disambiguate duplicates within a user by suffixing |
| `pcnames.Request` / `.Value` | `commands` rows | in-flight commands are **not** migrated — they are abandoned, which is correct: any command pending at cutover is stale by definition |
| `pcnames.Time` | `devices.last_seen_at` | parse, assume `Europe/London`, convert to UTC |
| `reminders.UserID` | `reminders.user_id` | preserved |
| `reminders.Reminder` | `reminders.body_ciphertext` | decrypt-CBC then encrypt-GCM per §7 |
| `reminders.Date` + `.Time` | `due_at_utc`, `due_local_time`, `timezone` | combine, localise using the user's tz (default `Europe/London`), convert to UTC |
| `reminders.Completed` | `is_completed` + `completed_at` | `completed_at` unknown for historic rows → NULL |
| `reminders.Recurrence*` (5 cols) | `reminders.rrule` | translated where parseable; unparseable values logged and set NULL (no client reads them today, so the risk is nil) |
| `verifications` + `verificationtypes` | `auth_challenges` | codes **not** migrated — all in-flight resets are invalidated and users re-request. Migrating them would mean carrying plaintext codes across. |
| `links` + `menupages` | `nav_items` | union, dedupe on `url`, `placement` derived from which table it came from |
| `feedback` | `feedback` | `Rating TEXT` → `TINYINT`, unparseable → NULL |
| `mailing_list` | `mailing_list` | generate `unsubscribe_token` for each row |
| `apikeys`, `requests`, `time`, `code` | *dropped* | dead |

## 9. Backup and recovery

| Property | Target |
|---|---|
| RPO (max data loss) | 24 h from nightly dump; 5 min once binlog shipping is enabled in Phase 1 |
| RTO (max downtime) | 1 h |
| Backup | Nightly `mysqldump --single-transaction`, `age`-encrypted, pushed off-host |
| Retention | 30 daily, 12 monthly |
| **Restore rehearsal** | **Monthly, automated in CI**: restore the latest backup into a scratch MySQL container, run the §5.1 verification queries plus a row-count assertion, fail the job on mismatch |

The rehearsal is the part that is usually skipped and is the reason backups fail when needed. It is
a CI job, not a calendar reminder.
