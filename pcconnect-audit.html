Security

18 findings

The system's threat model is unusual: a stolen credential does not leak data, it powers off, locks, or hibernates a physical machine. Several findings below hand that capability over cheaply.

CriticalSEC-01api

Live production database credentials sit in a file git is not ignoring

api/db_config.php

Host 130.162.164.140, user pcconnect_new, and a plaintext password are hardcoded. The file is currently untracked but not ignored — git check-ignore returns nothing for it, so a single git add . publishes the production database to history. These credentials are not yet in any commit, which is the one piece of good news, and it is a matter of luck rather than configuration.

Do now: rotate the MySQL password, add api/db_config.php to .gitignore, and move the values to environment variables. Verify the database is not reachable from the public internet.

CriticalSEC-02api

hCaptcha secret key is hardcoded in a public-facing script

api/signup.php:15

The server-side hCaptcha secret is embedded as a literal in the signup handler. A secret key lets anyone forge captcha verification against your site key, which turns the signup form into an unthrottled account-creation endpoint. Same remediation shape as SEC-01: rotate at hCaptcha, then read from the environment.

CriticalSEC-03api_node

Password change writes the new password to the database in cleartext

api_node/routes.js:323-332

The profile endpoint compares user[0].Password !== oldPassword and then stores newPassword verbatim:

updates.push("Password = ?");
values.push(newPassword);

Everywhere else in the system the Password column holds a SHA-256 hex digest. Any account that changes its password through this route ends up with a raw password in a column the rest of the system treats as a hash — so the account can no longer log in, and the plaintext is now at rest. validatePassword() exists in helpers.js with sensible rules and is never called from anywhere.

CriticalSEC-04all

The stored password hash is itself the credential

App/.../LoginActivity.java:127 · PCClient/PCClient/Login.vb:95 · frontend/src/lib/api.ts:3

Every client hashes the password with unsalted SHA-256 before transmitting it, and the server compares that digest directly against the Password column. This means the column contents are a working login credential — anyone with read access to the users table can authenticate as any user without cracking anything. It also means the "hashing" provides no protection at all: the digest is the password, transmitted and stored identically.

Compounding it: SHA-256 is unsalted and fast, so the same password produces the same digest for every user, and the Password varchar(64) column is sized exactly for SHA-256 hex, leaving no room for a modern hash format without a migration.

Fix shape: send the real password over TLS, hash server-side with bcrypt or argon2id, widen the column, and migrate on next successful login.

CriticalSEC-05App · PCClient

Login succeeds on any response that isn't the exact failure string

App/.../LoginActivity.java:158 · PCClient/PCClient/Login.vb:98

Both clients decide authentication by string equality against the literal "Invalid username or password.":

if (!"Invalid username or password.".equals(resp)) {
    SharedPrefManager.getInstance(...).setApiKey(resp);
    goToMain();
}

Neither checks the HTTP status code. A PHP warning, a maintenance page, a WAF block page, a 500 body, or a captive-portal interception are all stored as the API key and treated as a successful login. The user lands in the authenticated UI holding a garbage credential, and every later request fails with no explanation.

CriticalSEC-06PCClient

A network error is reported to the user as a successful login

PCClient/PCClient/Login.vb:37-88

LoginFunction has Return statements on its success paths but none in its three Catch blocks, so a connection failure falls out of the function returning Nothing. With Option Strict Off the caller's If output <> "Invalid username or password." coerces Nothing to an empty string, the comparison is true, and the client saves the credentials, shows "Login Successful.", and starts the polling loop with apiKey = Nothing.

CriticalSEC-07api_node · DB

The API key is simultaneously the session token and the AES key, and the server holds both

api_node/helpers.js:89 · PCClientWails/internal/reminders/reminders.go:151

Reminders are AES-256-CBC encrypted with the user's API key used directly as the key bytes. That key is stored in plaintext in users.api_key, one row away from the ciphertext in reminders.Reminder. Anyone who can read the database can decrypt everything, so the encryption buys nothing against the threat it appears designed for.

It is also not end-to-end: fetchUserReminders() decrypts server-side before responding, so the plaintext transits the server anyway. Three further consequences — the ciphertext has no authentication tag (CBC without HMAC is malleable), the decryptors disagree (Node has a legacy double-base64 heuristic that Go lacks), and rotating an API key permanently orphans every reminder that user has ever created, which is likely why no rotation mechanism exists.

HighSEC-08api_node

A real user's API key is committed across six documentation files

api_node/CREATION_REPORT.md · INDEX.md · MANUAL_TEST_REPORT.md · QUICK_START.md · README_TESTING.md · TEST_MANIFEST.md

The key 51359fd1b13802000649a6bd2f3f10ba, described in those files as belonging to the admin user (ID 1), appears in curl examples and test fixtures. It is in git history, so deleting the lines is not sufficient. Revoke and reissue the key; if this repository is or ever becomes public, treat it as fully compromised.

HighSEC-09App

The biometric gate silently disappears when biometrics aren't enrolled

App/.../MainActivity.java:171-174 · LoginActivity.java:89-92

Both biometric paths begin the same way:

if (bm.canAuthenticate() != BiometricManager.BIOMETRIC_SUCCESS) {
    sendStateChange(command, successMsg);   // proceed with no auth at all
    return;
}

Turning off fingerprint enrolment removes the protection rather than falling back to it — an attacker with the unlocked phone can shut down or lock the paired PC with a single tap. There is a second, subtler path to the same place: the capability check uses the deprecated no-argument canAuthenticate() (which evaluates BIOMETRIC_WEAK), while the prompt then requests BIOMETRIC_STRONG | DEVICE_CREDENTIAL. A device that can satisfy the prompt can still fail the check and skip authentication.

Fix: pass the same authenticator set to canAuthenticate() that the prompt requests, and on failure refuse the action rather than performing it. Also override onAuthenticationError, which is currently unimplemented in both classes.

HighSEC-10PCClient

A reminder popup blocks the entire keyboard system-wide

PCClient/PCClient/KeyboardBlocker.vb:27-33 · reminderWindow.vb:49

reminderWindow installs a low-level WH_KEYBOARD_LL hook on load that swallows every keydown and keyup unconditionally, and the window sets TopMost = True. The only exit is clicking Dismiss with a mouse. Combined with the fact that reminders are delivered from the server, this gives anyone holding a user's API key the ability to display an undismissable topmost window and disable the victim's keyboard — behaviour indistinguishable from a lock-screen attack, and a reliable way to get the binary flagged by endpoint protection.

The hook is also leaked on repeat: BlockKeyboard() overwrites hookID without unhooking the previous handle, and UnhookWindowsHookEx's return value is discarded. DismissB_Click calls the async Complete() without awaiting it, so an exception during the unhook path is silent.

HighSEC-11api_node

Clients declare their own privilege level and the server believes them

api_node/server.js:24,44 · internal/websocket/client.go:68

POST /v1/auth/session accepts clientType from the request body and stores it as role in the session, which then determines whether the socket is treated as a controllable desktop or a controlling phone. Nothing validates the claim against the device record, so any holder of an API key can register as either role for any PC name.

HighSEC-12api_node

CORS reflects any origin with credentials; socket.io accepts all origins

api_node/server.js:11, 62 · api/index.php:5

cors({ origin: true, credentials: true }) echoes back whatever Origin the caller sends and permits credentialed requests — the standard bypass of the same-origin protection that Access-Control-Allow-Origin exists to provide. The socket.io server separately sets cors: { origin: "*" }, and the PHP gateway sets Access-Control-Allow-Origin: * on an API authenticated by a custom header. The session cookie is also issued with secure: false and the comment "Since this runs locally", while the server binds 0.0.0.0:3000.

Restrict the origin list to the actual client origins, and set secure: true behind TLS.

HighSEC-13all

API keys have no expiry, no rotation path, and no rate limit protecting them

api/signup.php:102 · api_node/helpers.js:21-38

Keys are 16 random bytes generated once at signup and valid forever. There is no revocation endpoint, no last-used timestamp, no scope, and no per-IP or per-account throttle on /auth/login or on any key-authenticated route. A leaked key is permanent access to power-control commands, and login is brute-forceable at whatever rate the host allows. Rotation is additionally blocked by SEC-07, since rotating destroys the user's reminders.

HighSEC-14all clients

Every client stores the API key in plaintext at rest

PCClientWails/app/app.go:210-211 · App/.../SharedPrefManager.java:24 · PCClient/PCClient/Login.vb:101

The Go client writes the key into session.json even though internal/auth already stores it correctly in Windows Credential Manager — the code says so in its own comment: "keeping a masked or empty API key in JSON is safer, but for now we keep it". The Android app puts it in unencrypted SharedPreferences while the manifest sets allowBackup="true" with empty backup rules, so it travels into cloud backups and ADB backups. The VB client writes the password digest into user.config via My.Settings.

Given SEC-07, each of these files is also the decryption key for that user's reminders.

HighSEC-15DB

users.api_key has no index and no uniqueness constraint

DB/pcconnect_new_schema.sql:12

Every authenticated request runs SELECT id FROM users WHERE api_key = ?, and the column is a plain nullable varchar(512) — so each one is a full table scan, and the lookup is not constant-time. Without UNIQUE, nothing structurally prevents two accounts sharing a key. Add a unique index; it fixes an availability problem and a correctness problem at once.

MediumSEC-16api

Error handlers return internal exception text to the caller

api/index.php:60-63 · api/login.php:11 · api/signup.php:43

The gateway's catch-all ends with Response::error($e->getMessage(), 500), and both legacy scripts call die("Connection failed: " . $conn->connect_error) — which prints MySQL's connection error, including host and user, straight to the HTTP response. Log the detail server-side and return a generic message.

MediumSEC-17App

MainActivity is exported with no intent filter

App/app/src/main/AndroidManifest.xml:42-43

android:exported="true" without an <intent-filter> serves no purpose and lets any installed app launch the authenticated screen directly. Since onResume only redirects when the stored key is empty, a device with a saved session opens straight into the power-control UI, skipping the biometric prompt in LoginActivity. Set it to false.

Also over-declared: WRITE_EXTERNAL_STORAGE, which is a no-op above API 29 and is never used in the codebase.

MediumSEC-18api_node

Sessions live in a plain object that only grows

api_node/server.js:20

const sessionTokens = {} is never pruned. The cookie carries a maxAge, but that is enforced by the browser, not the server, so entries persist for the process lifetime and the map grows without bound. The Go client requests a fresh token on every reconnect attempt, and its reconnect loop retries every 2–5 seconds indefinitely, so a client that cannot reach the socket adds a permanent entry roughly every few seconds. Sessions are also lost entirely on restart, and cannot be shared if the API is ever run with more than one process.

Architecture

9 findings

The recurring pattern is abandoned migrations: three successive rewrites of the backend, none finished, none removed, with the shipped clients still pointed at the oldest one.

CriticalARC-01api

The PHP front controller cannot start — half its classes are empty files

api/src/Database.php · Auth.php · Router.php · Controllers/AuthController.php

api/index.php requires seven files and instantiates Database, Auth, Router, and three controllers. Four of those files are 0 bytes and ReminderController.php is 3 bytes containing }}. Any request to this endpoint is an immediate fatal error. Only Response.php and DeviceController.php have real content.

This matters beyond the endpoint: api_spec.md documents this API as the current architecture, so the specification describes a surface that has never run.

HighARC-02repo

Four API contracts, and the shipped clients use the one that isn't here

App/.../NetworkUtils.java:83 · PCClient/PCClient/PCClient.vb:11-17

The Android app (versionCode 702) calls api/pcconnect/exchange.php, PCNames.php, checkinternet.php, reminder.php, and listreminders.php. The VB client calls a different family under api/pcclient/ — findrequests.php, updaterequest.php, updatepctimedatabase.php, getreminder.php, completereminder.php, addpc.php. Neither directory exists in this repository. The production server is running code that is not under version control.

The contracts also disagree where they overlap: the clients expect checkinternet to return the string "yes", while both in-repo implementations return "Pong"; the Android app posts dates as dd/MM/yyyy, which normalizeDateToSql in routes.js rejects as an invalid date.

First step: recover the live PHP into the repository before changing anything else — it is currently the only copy.

HighARC-03repo

The working tree and HEAD describe two different projects

git status

166 tracked files are deleted in the working tree — the entire PCClientWails/, api_node/, and DB/ script trees. In their place are eight untracked paths: PCClient/ and the api/ PHP files. Nothing is staged, nothing is committed, and the branch is Mobile-App while main is the integration branch.

Whatever the intent, the current state is unrecoverable by anyone but you and unreviewable by anyone at all. Decide which tree is authoritative and commit that decision; the untracked api/ tree in particular exists in exactly one place on disk.

HighARC-04PCClientWails

Logging out on every shutdown

PCClientWails/main.go:47-48

OnShutdown calls applicationInstance.ClearSession(), which deletes the API key from Credential Manager and removes session.json. Closing the app is a full logout, so the user re-enters credentials on every launch — and SetAutoStart exists specifically to launch the app at boot into that state. The shutdown hook should stop the websocket manager and scheduler, not clear credentials.

MediumARC-05frontend

The webview hardcodes localhost:3000 and ignores the configured base URL

frontend/src/lib/api.ts:9 · frontend/src/lib/socketClient.ts:4

Session.BaseURL is a first-class field: SaveSession in Go validates it as required, persists it, and derives the websocket URL from it. The TypeScript layer then defines const API_BASE_URL = 'http://localhost:3000/api_node' and never reads the session value. The desktop client therefore cannot be pointed at the production server from its own UI, and all traffic is plaintext HTTP.

connectSocket(session) compounds this — it accepts a session parameter and uses none of it, connecting anonymously to http://localhost:3000. The server's socket middleware rejects any connection without a valid auth_token cookie, and the webview never obtains one (the Go layer does the cookie handshake in its own HTTP client). That connection cannot succeed as written.

MediumARC-06PCClientWails

Two Wails major versions in one module

PCClientWails/go.mod:11-12

wails/v2 v2.12.0 and wails/v3 v3.0.0-alpha.90 are both direct dependencies. main.go and app/app.go use the v2 runtime; android/main_android.go and the two iOS option files use v3's pkg/application. The mobile targets are behind build tags so the desktop build works, but the module carries a full alpha framework plus its transitive tree — including go-git, echo, and circl — for code that cannot currently be built alongside the desktop app.

MediumARC-07DB

No uniqueness on (UserID, PCName), and the code races on it

DB/pcconnect_new_schema.sql:15-23 · api_node/helpers.js:55-61

requirePC does a SELECT and then an INSERT if nothing came back. Two concurrent requests from the same PC both find nothing and both insert, and the schema has no constraint to stop them. Because commands are addressed by PCID, a duplicated device row means commands land on a PC record the client is no longer reading from. Add UNIQUE KEY (UserID, PCName) and switch to INSERT ... ON DUPLICATE KEY UPDATE.

Auto-registration is also unbounded: any valid key plus an arbitrary PCName header creates a row, with no cap per account.

MediumARC-08DB

Dates and timestamps stored as varchar(255), written in a format MySQL cannot parse

DB/pcconnect_new_schema.sql:6,10 · api/signup.php:80

DateOfBirth, DateTimeOfSignup, and pcnames.Time are all strings. Signup writes the timestamp with date("Y-m-d h:i:sa") — lowercase h is 12-hour and a appends am/pm, producing values like 2026-09-02 04:15:30pm. They sort incorrectly as strings and cannot be cast to DATETIME. Meanwhile pcnames.Time is the heartbeat the spec uses to decide whether a device is online within a 5-second window, evaluated as string data.

LowARC-09repo

No CI, and the only unit test covers the only unused package

PCClientWails/internal/realtime/policy_test.go

There is no .github/, .gitlab-ci.yml, or any other pipeline config. policy_test.go is the single real test in the repository, and internal/realtime is imported by nothing — the fallback-polling policy it encodes was never wired up. The Android tests are the untouched Android Studio stubs. api_node/package.json declares jest and supertest as devDependencies while its test script is echo "Error: no test specified" && exit 1; the actual testing is six ad-hoc scripts (run_tests.js, run_tests2.js, test2.js, test_all_endpoints.js, test_reminders.js) that must be run by hand against a live database.

Technical debt

15 findings

Correctness bugs and maintenance load that aren't security issues but will keep producing them. The VB client accounts for a disproportionate share.

HighDEBT-01PCClient

The desktop client makes roughly twelve HTTP requests per second, forever

PCClient/PCClient/PCClient.vb:247-375

Running() is a While True loop with a 0.5-second delay, and each pass issues six requests: get server time, post the time back, check internet, poll for requests, list reminders (twice — once via GetRemindersFunction() and once inline), and fetch the next reminder. That is ~12 requests per second per installed client, sustained. GetRemindersFunction creates a fresh HttpClient inside a Using block on every pass, so each one leaves a socket in TIME_WAIT — the classic route to port exhaustion.

The websocket design in api_node exists precisely to replace this loop.

HighDEBT-02DB

The upload script drops thirteen production tables inside an un-rollbackable transaction

DB/upload_remote.py:24-25

Before importing, run_sql_file executes DROP TABLE IF EXISTS across users, pcnames, reminders, and ten others. The whole body is wrapped in try/except ending in connection.rollback() — but DDL in MySQL causes an implicit commit, so the drop cannot be rolled back. Any failure during the import leaves the database empty with no recovery path, and the connection details at the top are placeholdered '##', meaning whoever runs it fills in production by hand.

The parser is also unsafe for this data: it treats any line ending in ; as a complete statement, which breaks on semicolons inside reminder text or feedback strings.

HighDEBT-03PCClient

Async calls are fired and forgotten; exceptions are caught into empty blocks

PCClient/PCClient/PCClient.vb:251, 314, 363-372 · ControlPanel.vb:91

GetRemindersFunction(), Running(), Complete(), AddReminderFunction(), and reminderWindow.Running() are all declared Async Function ... As Task and all invoked without Await. Faults inside them are never observed, and the code immediately after reads state the task has not finished writing — ControlPanel.RemindersTextEdit(ReminderListTextBox) runs on the line after GetRemindersFunction() is launched.

The main loop's handler is worse than silent, it is deliberately empty:

Catch ex As Exception
    If ex.Message.Contains("An error occurred while sending the request.") Then
        ControlPanel.internetChange(0)
    ElseIf Not ex.Message.Contains("System.Collections.Generic.Dictionary") Then
        ' nothing
    End If
End Try

Every parse failure, null reference, and HTTP fault in a 100-line loop body disappears here.

HighDEBT-04PCClient

The internet-status flag is set to the opposite of what it displays

PCClient/PCClient/ControlPanel.vb:30-47

internetChange(0) sets Internet = 1 and shows "Not Connected"; internetChange(1) sets Internet = 0 and shows "Connected". The caller then guards on the field — If ControlPanel.Internet = 0 Then internetChange(1) — so the guard is inverted relative to the label the user sees, and the status indicator updates on the wrong transitions.

MediumDEBT-05PCClient

The reminder list string is appended to but never cleared

PCClient/PCClient/PCClient.vb:213-244

GetRemindersFunction concatenates every reminder onto ReminderListTextBox without resetting it first, and it runs twice per second from the polling loop. The string grows without bound for the life of the process, and the control panel shows the same reminders repeated once per poll. The inline copy of the same logic in Running() does reset it — the two implementations of identical formatting disagree, and one of them is wrong.

MediumDEBT-06PCClientWails

Stop() cannot close the websocket because the connection is never stored

PCClientWails/internal/websocket/client.go:79-98, 213-221

connectLoop dials into a local conn and passes it to readLoop, but never assigns m.conn — the field is only ever set to nil. Stop() cancels the context and then closes m.conn, which is always nil, so the goroutine stays blocked in conn.ReadMessage() until the server drops it. ClearSession and reconnect both call Stop(), so a logout or a settings change leaks a goroutine and an open socket that is still delivering commands.

MediumDEBT-07PCClientWails

Reminders re-fire every year on the same date

PCClientWails/internal/reminders/reminders.go:117-124

The scheduler builds a cron expression from the reminder's own timestamp:

fmt.Sprintf("%d %d %d %d %d *",
    Second, Minute, Hour, Day, Month)

Cron has no year field, so 0 30 9 15 3 * means "09:30:00 on 15 March, every year" rather than once in 2026. A one-off reminder becomes an annual one for as long as the client runs.

MediumDEBT-08PCClientWails

The scheduler keeps the API key it was constructed with

PCClientWails/app/app.go:132 · internal/reminders/reminders.go:178

startWebSocket guards scheduler creation with if a.scheduler == nil, so the key captured on first login persists across every later SaveSession. Signing in as a different account leaves the scheduler decrypting with the previous user's key. Given SEC-07 this fails closed rather than leaking, but it fails quietly — the resulting reminders read "Error decrypting", which the frontend rewrites to "Reminder text unavailable" and shows as normal content.

The decryption path is itself lenient: DecryptReminder returns nil error with raw bytes when PKCS#7 padding is invalid, so a wrong key yields binary garbage presented as a successful result rather than a detectable failure.

MediumDEBT-09App

Android polls every five seconds regardless of lifecycle, from leaking AsyncTasks

App/.../MainActivity.java:66-69, 119, 260

internetChecker reschedules itself every 5 seconds and is only cancelled in onDestroy, so it keeps running while the activity is backgrounded. CheckInternetStatusTask is a non-static inner class — it holds an implicit reference to the Activity and calls btnSleep.setEnabled(...) in onPostExecute, so an in-flight task after a configuration change touches a dead view hierarchy. AsyncTask has been deprecated since API 30 and the app targets 35.

Move the cancel to onPause and replace AsyncTask with the OkHttp client the class already uses elsewhere.

MediumDEBT-10App

A field initializer reads a singleton before the activity has a context

App/.../ListRemindersActivity.java:23

Suggested order

Remediation sequence

Ordered by dependency rather than severity — some fixes are blocked until an earlier one lands.

1

Rotate the three exposed secrets, today

The MySQL password, the hCaptcha secret, and the admin API key. The first two are not yet in git history and the third is — treat that one as already public. Then add api/db_config.php to .gitignore so it stays out.

SEC-01 · SEC-02 · SEC-08

2

Get the live PHP under version control

The api/pcconnect/ and api/pcclient/ directories that both shipped clients depend on exist only on the production server. Until they are committed, no refactor is reversible and no outage is recoverable. Resolve the working tree at the same time, so there is one authoritative state.

ARC-02 · ARC-03

3

Fix the two authentication paths that fail open

Check HTTP status before parsing login responses, and return an explicit failure from the VB catch blocks. Make the Android biometric gate refuse the action when it cannot authenticate rather than performing it. These are small, local, and independently shippable.

SEC-05 · SEC-06 · SEC-09

4

Separate the three jobs the API key is doing

Password verification, session identity, and reminder encryption are all the same 32-character string today, which is what makes key rotation destructive and makes a database read equivalent to full account access. Server-side bcrypt for passwords, a separate rotatable session token, and a per-user key derived independently of the credential. Add UNIQUE and an index to api_key while you are in the schema.

SEC-03 · SEC-04 · SEC-07 · SEC-13 · SEC-15

5
